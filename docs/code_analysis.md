# UPS Firmware Code Analysis

This document explains the authored firmware in the repository, how the modules fit together, what assumptions the current design makes, and what the present validation work can and cannot prove.

It focuses on the project-authored modules, not the autogenerated STM32 HAL/CubeMX support files.

## High-Level Architecture

The firmware is organized around one top-level supervisor and two device-specific drivers:

- [app_supervisor.c](C:/Users/john/OneDrive/Documents/GitHub/UPS/STM32CubeIDE/Core/Src/app_supervisor.c)
- [bq25730.c](C:/Users/john/OneDrive/Documents/GitHub/UPS/STM32CubeIDE/Core/Src/bq25730.c)
- [mpq5031.c](C:/Users/john/OneDrive/Documents/GitHub/UPS/STM32CubeIDE/Core/Src/mpq5031.c)
- [board_config.c](C:/Users/john/OneDrive/Documents/GitHub/UPS/STM32CubeIDE/Core/Src/board_config.c)
- [main.c](C:/Users/john/OneDrive/Documents/GitHub/UPS/STM32CubeIDE/Core/Src/main.c)

The design is intentionally simple:

- `main.c` initializes the MCU peripherals and calls the supervisor in a polling loop.
- `board_config.c` centralizes the current wiring assumptions and phase-1 tuning values.
- `app_supervisor.c` is the state machine that decides when to probe, configure, poll, and fault.
- `bq25730.c` encapsulates charger register access and phase-1 charger programming.
- `mpq5031.c` encapsulates USB-C source-controller register access and phase-1 source configuration.

The result is a small, debugger-friendly bring-up architecture with very little hidden control flow.

## Module Roles

### main.c

`main.c` is a thin integration layer.

Responsibilities:

- initialize the HAL
- configure clocks
- initialize GPIO and I2C1
- build the current `board_config_t`
- initialize the supervisor
- update the validation snapshot each loop iteration

Why it matters:

- this file defines the polling cadence
- this file defines the MCU-side interpretation of the hardware wiring
- this file now exposes `g_validation_debug`, which is the main observability surface during board bring-up

Current limitation:

- the GPIO inputs are configured with `GPIO_NOPULL`, which is correct for the intended PCB if external biasing exists, but problematic on a bare MCU dev board where inputs may float

### board_config.c / board_config.h

This module captures the current hardware assumptions.

Notable contents:

- I2C addresses for BQ25730 and MPQ5031
- startup and polling intervals
- BQ voltage and current settings
- MPQ PDO current setting
- GPIO port/pin mapping for LED, `PROCHOT_N`, `CHRG_OK`, `VSEL1`, and `VSEL2`

Why it matters:

- this is the canonical source of truth for phase-1 behavior
- both runtime behavior and validation expectations derive from these values

Current limitation:

- there is only one hard-coded configuration profile
- there is no explicit dev-board configuration profile yet

### app_supervisor.c / app_supervisor.h

This is the behavioral core of the firmware.

State flow:

- `APP_BOOT`
- `APP_WAIT_POWER_STABLE`
- `APP_PROBE_DEVICES`
- `APP_READ_BASELINE`
- `APP_CONFIGURE_BQ`
- `APP_CONFIGURE_MPQ`
- `APP_RUN`
- `APP_FAULT_HOLD`

Fault flow:

- `APP_FAULT_PROCHOT_ASSERTED`
- `APP_FAULT_BQ_NOT_PRESENT`
- `APP_FAULT_MPQ_NOT_PRESENT`
- `APP_FAULT_BQ_CONFIG`
- `APP_FAULT_MPQ_CONFIG`
- `APP_FAULT_BQ_STATUS`
- `APP_FAULT_I2C`
- `APP_FAULT_CONFIG_VERIFY`

Why it matters:

- the supervisor is where hardware assumptions become firmware behavior
- most validation effort should target this file because it contains the system-level policy

Important behavior:

- `PROCHOT_N` is checked before any state-specific work
- charger faults are latched into `APP_FAULT_HOLD`
- runtime polling uses a faster interval than fault hold
- LED behavior is state-derived and doubles as a coarse debug interface

Current limitation:

- fault recovery is intentionally absent
- once the system faults, it stays faulted and only refreshes snapshots
- that is good for first bring-up, but it means transient bad samples can stop the system immediately

### bq25730.c / bq25730.h

This driver handles the charger IC.

Responsibilities:

- prove the expected device exists
- read the register set needed by the supervisor
- encode phase-1 charge and input limits
- write and verify those values
- report status faults via `charger_status`

Why it matters:

- this module translates human-readable current/voltage targets into the device register space
- configuration verification happens here, not in the supervisor

Current limitation:

- only one configuration phase exists
- the driver is synchronous and blocking
- there is no retry/backoff policy beyond immediate faulting

### mpq5031.c / mpq5031.h

This driver handles the USB-C source controller.

Responsibilities:

- prove the expected vendor-coded device exists
- preserve the first read-clear status sample
- read baseline and runtime register sets
- apply the current source-capability configuration
- verify key control bits after writes

Why it matters:

- the MPQ configuration controls what the board presents to the outside world as a source
- the preserved first status sample is useful because some status bits clear on read

Current limitation:

- this is still a phase-1 policy only
- more advanced Type-C / PD state handling is not modeled at the application layer yet

## Current Bring-Up Interpretation

From the observed dev-board run:

- the firmware executed
- the validation snapshot initialized correctly
- the supervisor entered `APP_FAULT_HOLD`
- the last fault was `APP_FAULT_PROCHOT_ASSERTED`

That means the current blocker is not that the state machine is dead. It is that the MCU believes `PROCHOT_N` is asserted.

Most likely explanations on a bare MCU dev board:

- `PA0` is floating low
- `PA0` is externally pulled low on the dev board
- the test wiring does not match the intended PCB net behavior
- the signal polarity assumption is wrong for the temporary setup

This is exactly the kind of issue the new simulation and debugger snapshot are meant to surface early.

## What the Host-Side Simulation Proves

The simulator in [run_supervisor_sim_tests.py](C:/Users/john/OneDrive/Documents/GitHub/UPS/scripts/run_supervisor_sim_tests.py) mirrors the supervisor logic and validates:

- nominal boot reaches `APP_RUN`
- `PROCHOT_N` low faults immediately
- missing BQ faults correctly
- missing MPQ faults correctly
- runtime I2C failure faults correctly
- BQ status faults correctly
- fault polling cadence changes correctly

What it does prove:

- the intended state machine behavior
- the expected fault classification
- the expected ordering of probe/configure/poll logic

What it does not prove:

- electrical behavior
- analog power-path behavior
- USB-C signal integrity
- actual charger operation
- actual GPIO biasing on hardware

## Risks and Design Gaps

### 1. Floating digital inputs on dev boards

Risk:

- on bare MCU hardware, inputs like `PROCHOT_N`, `CHRG_OK`, `VSEL1`, and `VSEL2` may float

Impact:

- false faults
- misleading bring-up results

Likely fix:

- add a dedicated dev-board mode with internal pulls or software overrides

### 2. No separation between intended PCB mode and dev-board mode

Risk:

- temporary bring-up wiring gets judged against final-board assumptions

Impact:

- false negatives during early firmware validation

Likely fix:

- add a second board configuration profile or compile-time bring-up profile

### 3. Synchronous bus access everywhere

Risk:

- any transient I2C issue becomes an immediate system fault

Impact:

- fragile early bring-up

Likely fix:

- later introduce retries or a more nuanced runtime error policy once hardware is stable

### 4. No automated host/native build of production C code

Risk:

- the simulator mirrors the logic but is still a parallel implementation

Impact:

- drift is possible if the C state machine changes and the simulator is not updated

Likely fix:

- eventually add a native C test harness or generated bindings if you want stronger equivalence

## Recommended Next Step

The most pragmatic next change is a `DEV_BOARD_MODE` or similar profile that:

- biases `PROCHOT_N` to a known-safe state for MCU-only testing
- optionally biases `CHRG_OK`, `VSEL1`, and `VSEL2`
- preserves the current PCB-intended behavior as the default production configuration

That would let you continue validating the rest of the state machine on the dev board instead of stopping at the first floating-input fault.
